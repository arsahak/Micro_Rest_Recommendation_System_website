Technology Stack — Micro-Rest Recommendation System

Verified against the two repositories' package.json files rather than assumed. Two repos, two roles: website/ is the participant-facing app; backend/ is a shared Express API that also serves an unrelated set of apps (admissions, exams, fees, orders, products, a chatbot) on the same MongoDB database. The fatigue-study feature lives in a specific slice of its collections and routes.

Not used, despite being common in similar stacks — worth knowing so no one goes looking for them:
  • Framer Motion — not installed. Interactive states (hover, transitions, the notification bell dropdown) are done with plain CSS transitions and conditional Tailwind classes.
  • Auth.js / NextAuth — not installed. Authentication is a small, custom, PIN-based flow (see below) — there's no session provider, no OAuth, no adapter.

Client-side data fetching goes through lib/api.ts, which resolves to /api/proxy/* in the browser (a same-origin Next.js Route Handler that forwards the request server-to-server to the Express API) and calls the Express API directly when running in a Server Component/Action. This avoids CORS entirely and keeps the backend URL out of client-side code.

The website never calls the Express API's real URL directly from the browser — every client-side request is same-origin through the proxy, which reads the participant's JWT from an mrrs_token cookie (or localStorage on the client) and attaches it as Authorization: Bearer <token> before forwarding.

Authentication model

There is no username/password or OAuth. A participant signs in with:

  • Participant ID — P01 through P10
  • PIN — a short numeric/string PIN. On a participant's very first login, whatever PIN they type becomes their permanent one (hashed with bcrypt); after that, it's checked normally.

On success, the backend issues a JWT ({ userId: participant_id, role: "participant" }) valid for 30 days, stored in localStorage and mirrored to a plain (non-httpOnly) cookie so server-rendered pages and Route Handlers can read it too.

Every participant-scoped endpoint enforces that a "participant"-role token can only ever read or write its own participant_id — regardless of what ID is passed in a query string or request body. Non-participant roles (staff/researcher accounts, used for the aggregate research dashboard) are unrestricted. This was verified under real concurrent multi-participant load, not just single-request testing.

Notifications

Two independent channels, both driven from the same backend logic:

  • Persisted, in-app — every notification-worthy event is written to notificationlogs and surfaced in the website's notification bell via GET /api/sessions/notifications (ownership-scoped, like everything else).
  • Native OS notification — the browser's Notification API, requested explicitly via a button on the dashboard (not auto-prompted at login). Fired silent: true — visual only, no sound.

Both are best-effort: if browser notification permission is denied, the in-app bell entry is still created and visible; the native toast is simply skipped, and the UI now says so explicitly rather than failing silently.
